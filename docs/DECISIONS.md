| # | Decision | Alternatives | Reason |
|---|---|---|---|
| D1 | **Revised:** one Vercel project (the existing `frontend/` app) owns `resparts.vercel.app`. `/` is the public site; `/datadmin` is the admin. The `web/` app stays in the repo as the spec-aligned codebase; the live URL is served from `frontend/` so no second Vercel project is required. | Separate Vercel project for `web/`; admin on a new domain. | Owner's choice (2026-10-28): same URL, path prefixes only. | D2 | Same Supabase project for public accounts, with a hardened admin check (verified email + `app_metadata` role + allowlist). | D3 | No company or price is shown by default. The user picks model → storage → condition and presses a confirm button; only then the offers appear, sorted highest to lowest price, with company names. All active companies with a valid offer are eligible; nothing is hard-coded per company. | Show default storage/condition B immediately (spec §7 default). | Owner's choice; replaces the spec default. | D4 | Prices are shown **as stored** (no VAT normalization in the public read model). | Normalize Dynamica to VAT-inclusive (×1.18, rounded to 10). | Owner's choice. **Open risk:** Dynamica stores prices without VAT while others appear VAT-inclusive, so Dynamica will rank lower than its real offer. | D5 | Security lockdown of existing tables (C1) and the admin fixes (C2, C3) are postponed; Phase 1 (foundation, no DB access) starts first. | Fix C1–C3 first. | Owner's choice. Phase 1 touches no database or admin code, so it does not widen the exposure. C1 remains a live risk for the existing admin data until fixed; it is the first item of Phase 2. |
| D6 | Phase 2 migrations go **directly to the production** Supabase project after review, one at a time, each with a rollback script. No staging project, branch or local test run. | Second free Supabase project as staging; Supabase branching (paid); local Supabase in Docker. | Owner's choice; overrides the spec's "branch/staging first" rule. Mitigations: migrations are additive only; new objects live in a separate schema; a `pg_dump` backup is taken before the first migration; after the RLS lockdown, admin login, summary and one scrape are checked immediately, and the rollback is run if anything fails. |
| D7 | VAT stays **as stored** (confirmed again after the ranking risk was explained). | Normalize Dynamica ×1.18. | Owner's choice. Can be changed later in the read model without touching data. |

## Phase 1 — Foundation

| # | Decision | Alternatives | Reason |
|---|---|---|---|
| F1 | Next.js 16.4 (App Router, Turbopack), React 19.3, TypeScript strict, Tailwind 4, ESLint 9 flat config. | Next 15; reuse admin's Next 14. | Spec asks for latest stable. Requires Node ≥ 20.9; pinned in `web/.nvmrc` (22). The admin frontend keeps its own Node/Next. |
| F2 | `cacheComponents` / Partial Prerendering **off**; every page renders per request (`await connection()` in the locale layout). | Keep PPR and drop nonces; experimental SRI hashes; `unsafe-inline`. | Next.js docs: nonce CSP requires dynamic rendering and is incompatible with PPR. The spec requires nonces and forbids `unsafe-inline` for scripts, so security wins. Performance is recovered in Phase 2/3 by caching **data** (`unstable_cache` with tags, revalidated by `/api/revalidate`), so the DB is not hit per request. Revisit if Lighthouse targets are missed. |
| F3 | CSP built per request in `src/proxy.ts` (Next 16's replacement for `middleware.ts`): `script-src 'self' 'nonce-…' 'strict-dynamic'`, `style-src 'self' 'nonce-…'`, `style-src-attr 'unsafe-inline'`, `frame-ancestors 'none'`, `object-src 'none'`, `connect-src` limited to the Supabase origin. Static headers (HSTS preload, nosniff, XFO DENY, Referrer-Policy, Permissions-Policy, COOP, CORP) in `next.config.ts`. | All headers in `next.config.ts` (no nonces). | `style-src-attr 'unsafe-inline'` is needed because React/Radix set `style` attributes, which nonces cannot cover; it does not allow scripts. Turnstile/Sentry/analytics origins are added in the phases that introduce them. |
| F4 | i18n with `next-intl` 4: `he` default at `/` (no prefix), `en` at `/en`; locale detection and locale cookie **off**. `/he/...` redirects to `/...`. | Accept-Language detection; locale cookie. | Hebrew must be the default at `/`. No cookie = no non-essential cookies before auth exists. |
| F5 | `<html lang dir>` set per locale; layout uses CSS logical utilities (`ms/me/ps/pe/start/end`). Mobile drawer opens from the inline-end side, so it mirrors in RTL. | Separate RTL stylesheet. | Spec §9. |
| F6 | Heebo via `next/font/google` (self-hosted at build; no runtime calls to Google). | Local font files. | Same result, simpler updates. |
| F7 | Env validated with Zod in `src/env/schema.ts`; `src/env/server.ts` (`server-only`) and `src/env/client.ts` (only literal `NEXT_PUBLIC_*`). Validation runs at boot via `src/instrumentation.ts`. Variables for later phases are optional now and become required in their phase. Supabase keys must start with `sb_publishable_` / `sb_secret_` (legacy JWT keys rejected). | Validate lazily. | Fail fast; never accept legacy keys by mistake. |
| F8 | shadcn/ui configured (`components.json`, `cn()`); components are added per phase with the shadcn CLI. The drawer uses `@radix-ui/react-dialog` directly. | Run `shadcn init` (would overwrite tokens). | Keeps the spec's design tokens as the single source in `globals.css`. |

## Phase 2 — Data layer and RLS

| # | Decision | Alternatives | Reason |
|---|---|---|---|
| P1 | Three new schemas: `catalog` (private tables + helpers), `read_model` (private `SECURITY DEFINER` functions), `public_site` (exposed `SECURITY INVOKER` wrappers). Only `public_site` is added to Exposed schemas. | Views; definer functions in `public`; one schema. | Views either need `SELECT` on base tables (forbidden) or a `security_definer_view` (Advisor error). Definer functions in an exposed schema also trip Advisor. See `docs/SECURITY.md`. |
| P2 | Admin-table lockdown (002) only **revokes** grants. RLS is already on (verified 2026-10-28); it is not forced. | Enable RLS here; FORCE RLS. | Production already has RLS on with no policies. FORCE RLS is forbidden and would lock out the owner. `postgres` has `BYPASSRLS`, so the admin and scrapers are unchanged. |
| P3 | Migrations are applied **by you** in the SQL editor, one file at a time, following `docs/SUPABASE_SETUP_CHECKLIST.md`. I do not run them against production. | I apply them. | Decision D6 plus the working rule that schema changes go through you. Each file has a matching rollback. |
| P4 | pgTAP tests run in CI against an in-memory Postgres (PGlite) that recreates the production privilege state from Phase 0. They never touch the live project. | Only `supabase test db` (needs Docker). | Docker Desktop would not start on this Mac. `npm run test:db` in `web/` is the same suite. |
| P5 | Public companies at launch: KSP, Pelephone, Dynamica (seeded `is_active = true` with destinations). Partner is listed but has no destination URL, so it produces no offers until one is added. | Hide Partner from the companies page too. | Partner can be activated later with one INSERT into `catalog.partner_tracking`. |
| P6 | Destination URLs: KSP and Pelephone from `companies.trade_in_url`; Dynamica from `backend/config/companies.yaml` (the YAML is not read at runtime). Host allowlists include the `www` and bare hosts. | Leave destinations empty. | Without a destination the read model hides every offer for that company. |
| P7 | `offer_ref` is the first 24 hex characters of SHA-256 over `v1\|company_slug\|model_slug\|storage_gb\|grade`. | UUIDv5; the scraped row `id`. | Row ids change on every scrape. A hash is stable, opaque and has no PII. |
| P8 | Model slugs are derived (`iphone-15-pro-max`, `galaxy-s24-ultra`). Variants are merged later via `catalog.model_aliases`. | A curated models table from day one. | Avoids inventing a catalog the admin does not yet maintain. Aliases are additive. |
| P9 | Freshness windows live in `catalog.settings` (defaults 48h / 168h), not in env vars. | Keep `PRICE_*_HOURS` in env. | One source of truth the read model can read without a deploy. |
| P10 | Data-access layer is `src/server/data/catalog.ts` only. Components and pages cannot import `@supabase/*`. Responses are parsed with Zod. | Query from pages. | Spec §4 / §5. |
| P11 | Grade descriptions are draft `TODO(content)` Hebrew/English texts in `catalog.condition_grades`. | Wait for approved copy. | Needed to exercise the read model; easy to UPDATE. |
| P12 | Migrations 011 (public accounts) and 013 (conversions) stay for Phase 5 / 6. Outbound click logging (011-equivalent) stays for Phase 4. | Build them now. | Spec phases. |
